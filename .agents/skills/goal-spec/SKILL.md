Prepare a single `/goal` command for an entire QBS feature spec. The user runs the generated command in a goal-capable session. This preparation session discovers facts, gathers required choices, and generates the command; it never dispatches agents or implements tickets.

Use the shared [orchestration-gate](../orchestration-gate/SKILL.md) for confidence, model planning, approval, cost status, and evidence vocabulary, and read the shared [goal prompt orchestration contract](../../goal-prompt-orchestration.md). Keep this skill portable: refer to the active environment's available sub-agent dispatch mechanism, and do not name or assume a particular harness.

## Discover

Find the repository root, primary worktree, default branch, and current branch. QBS keeps canonical `.specs/` and `.research/` in the primary worktree and exposes them to linked worktrees; use those shared paths as authoritative. Find every `spec.md` recursively below `.specs/`, including nested specs. For each candidate spec, inspect all implementation tickets, acceptance criteria, blockers, status, research references, implementation state, ticket handoffs, and research findings. Note whether `.specs/` is ignored.

Compute readiness from the graph. A ticket is ready when it is unfinished and every blocker is done and recorded as merged. With no run state, only tickets without blockers are ready. Compare the computed frontier with recorded state and report omissions. If there are no unfinished tickets, report that the spec is complete and generate no command. If unfinished tickets exist but none is ready, report the blockers and generate no command.

Read the selected spec's decisions, README, relevant build and CI configuration, project files, and applicable `AGENTS.md` or `CLAUDE.md`. Read research cited by the tickets, relevant prior ticket findings, and blocker handoffs. Treat code locations in research as leads pinned to a commit and verify drift against current code. Inspect enough current code to identify project rules, prerequisites, test seams, and any decisions that could change the implementation. Do not infer environment details from README alone.

Resolve the existing spec integration branch and base branch from the run state when present; otherwise default the integration branch to the spec directory name and the base to the repository's default branch. Establish the candidate starting SHA. An existing integration branch is reusable only when its recorded starting SHA matches. Do not create branches or worktrees in this preparation session.

## Plan and ask once

Build a complete sub-agent roster for the entire unfinished ticket graph. Use the named `implementer` for one isolated task per ready ticket; `merger` for serial integration and the shared execution records; `review-standards` and `review-spec` for each ticket's pre-merge review; `explorer` only when cross-ticket exploration is useful; and `red-team` only when an independent final challenge is warranted. Explicitly ask the user for the model profile and reasoning level for each selected non-orchestration role, including agents writing code, tests, reviews, and project records. Every role actually selected must have a purpose, capability, isolation, optionality, concurrency eligibility, reasoning level, and token range. Repeated role invocations use the approved role assignment unless the user customizes a ticket-level exception.

Build a ticket dispatch plan for every unfinished implementation ticket, including blocked tickets. Show one row per ticket with its scope, dependencies, implementer assignment, profile, resolved model, reasoning, estimated and approved budget, isolation, concurrency eligibility, and reserved fix capacity. The role roster must separately show resolved assignments for `review-standards`, `review-spec`, merger, and any selected optional roles, including invocation counts and aggregate budgets across tickets. Show workflow overhead for exploration, implementation, both review roles, merging, fixes, validation, integration, and optional red-team work. Keep token estimates, account quota, and monetary cost distinct; mark unavailable values unavailable or advisory, never zero or exact.

Resolve neutral profiles with the role-sensitive model catalog in `internal/agents/dispatch.go` against the active environment. Offer `Recommended`, `Economy`, `Deep`, and `Customize`; `Customize` must let the user assign a model profile and reasoning level to each selected role, including the two review roles and any optional role. Show the resolved model for every role and ticket. An unavailable profile or resolution is an actionable gate failure; do not substitute. Set a global implementation concurrency limit, defaulting to two, and reserve capacity for review, fixes, validation, and integration.

Present one preflight summary containing the request, confidence score and rationale, assumptions, unresolved questions, full role roster, selected plan, resolved assignments, ticket dispatch table, overhead budgets, optional-role status, concurrency, and cost-status fields. Apply the confidence gates from orchestration-gate. Clarify unresolved facts that could change intent. Get approval for the selected model and cost plan before generating a command. Once approved, the goal prompt must preserve these assignments and constraints; it must stop if the active environment cannot honor them.

Ask in one round, only for choices that change the command: which spec if there are several; confirmation or correction of the build, tests, prerequisites, base/integration branches, and concurrency; the model plan and explicit model/reasoning assignment for every selected sub-agent role; whether to include optional exploration or red-team work; and the goal turn limit. Do not ask the user to assign the orchestration model as though it were a worker. Recommend a turn limit based on the number and complexity of unfinished tickets. Do not offer blocked tickets as ready choices. If essential facts remain unresolved, ask only about those facts and continue independent discovery.

## Generate

Fill [template.md](template.md) with discovered facts and approved choices. Use absolute paths from the primary worktree, exact build and test commands, the initial frontier, all ticket paths and dependencies, relevant research pointers, branch names, baseline knowledge, prerequisites, test seams, and 2–3 compact project rules. Keep the prompt compact by pointing to canonical spec and ticket files rather than duplicating their contents. Do not run or dispatch the generated goal.

The generated goal establishes `S/implementation-state.md` as the spec run journal and `S/handoffs/NN.md` as each ticket's handoff. On the first run, record the immutable starting SHA, base and integration branches, baseline results, and initial frontier. Preserve existing run state and spec-level handoffs; do not replace a handoff from another run.

Preserve these execution invariants in the generated command:

- Implement the complete spec by working through its ticket graph. Run independent ready tickets concurrently only within the approved global, role, and budget limits. Recompute the frontier after each integrated ticket. Never dispatch a blocked ticket. Continue other ready tickets when one ticket blocks; finish only when all tickets are done or no unfinished ticket can proceed.
- Keep the canonical `.specs/` and `.research/` files in the primary worktree as shared QBS context. Implementers and reviewers treat them as read-only. After each merge, the approved `merger` acts as the single serial writer for ticket status, `implementation-state.md`, ticket handoffs, and that ticket's research findings. No other sub-agent edits these shared records. The orchestrator reads and verifies the completed records but does not author code or project documents, as required by the shared goal prompt orchestration contract.
- Use integration branch `B` from the approved base SHA. Never recreate or rebase `B`. For each ticket, create ticket branch `B-NN` from the latest `B` in an isolated worktree and give it to that ticket's implementer. Keep ticket branches separate. If `B` moved while a ticket was running, bring the latest `B` into that ticket branch and re-run relevant checks before integration. Resume an incomplete branch only when the run state identifies it; never overwrite an unrelated branch or dirty worktree.
- Before implementing each ticket, read its cited research and relevant earlier ticket findings, verify stale code pointers, check prerequisites, and map every acceptance criterion to a change and test seam. Include explicit `BLOCKED` outcomes for unresolved blockers, unavailable prerequisites, or impossible spec decisions.
- Test first, implement, run the exact build and relevant suites, and review every ticket branch against both project standards and the originating spec. Use the approved `review-standards` and `review-spec` assignments. Fix findings within the approved plan before asking the merger to integrate.
- Integrate completed tickets serially into `B` with `--no-ff`. The merger inspects the diff, merges, runs or verifies integration checks, and then records the merge SHA, ticket status, handoff, frontier, and `.research/<feature>/ticket-NN-implementation-findings.md` with evidence-backed findings and a `Still unclear or open` list. Choose the research feature directory by subject, even for nested specs. These shared-file updates happen one ticket at a time; no two agents write the same research file or run-state file. On a blocker or turn limit, the merger records current state and the remaining frontier. The orchestrator reads and verifies these files without authoring them.
- Read earlier findings before dispatching later tickets. Keep each completed ticket's notes available to every later implementer. Do not mark a ticket done unless all acceptance criteria are met and its merge and checks are recorded. Include what it unblocks in the handoff and state.
- Never weaken, skip, or delete tests. Record baseline failures and do not claim them as regressions. Keep `.specs/` and `.research/` changes local and uncommitted. Do not push, create a pull request, or modify the base branch.
- Clean up completed ticket worktrees and branches, preserving `B` and its final revision. The goal is complete only when all tickets are done, each has a handoff and findings note, the final integration checks pass, no `B-NN` ticket branches remain, and a spec-level `implementation-review-handoff.md` records requirement coverage, checks, review findings, final revision, assumptions, confidence, and remaining risks. If the turn limit arrives first, update state and report the exact remaining frontier.

Print the completed `/goal` command in one fenced `text` block. Below it, report the approved role/model assignments and concurrency, identify blocked and ready tickets, state what completion unblocks, and give the command's byte count. If no command is generated, explain why. Do not modify project files or run the generated goal.
